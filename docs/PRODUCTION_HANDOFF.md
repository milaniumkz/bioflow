## Что подготовлено

Партийный API `/api/v1/ledger`: добыча, распределение на перевозки, брутто/тара/нетто, приёмка с расхождениями и частями, отдельная разгрузка, остатки и резервы, мойка/производство с несколькими входами, точный материальный баланс, перемещения, отгрузки, возвраты, инвентаризация и корректировки. История связывает готовую продукцию с исходным сырьём, перевозками, озером и подрядчиком. Массы хранятся как Decimal с точностью 0,001 т.

Команды имеют ключи идемпотентности, выполняются в serializable-транзакциях и повторяют конфликтующие транзакции. Отмена создаёт обратные движения. Расход потреблённого выхода и отмена отгрузки с возвратом блокируются. SQL запрещает изменение/удаление движений и аудита. Ограничения прав проверяются при чтении, записи, выгрузке и скачивании файлов. Десять требуемых ролей сохранены вместе с совместимыми прежними ролями.

Веб и Android используют новый учёт. Мобильная очередь привязана к пользователю, сохраняет ключи команд и показывает серверные конфликты. Чтение ранее загруженных карточек и справочников доступно без сети. Загрузка новых фото требует связи. Встроены камера QR, фото документов, формы операций и уведомления. Геолокация и карты отсутствуют.

Отчёты: добыча, перевозки, расхождения, движения, исторические остатки/обороты, мойка, производство, потери, перемещения, отгрузки, сверка и аудит; CSV/XLSX/PDF. Отчёты выгружаются полностью, без прежних ограничений 500/80 строк. Для PDF предусмотрен шрифт с кириллицей.

Внутренние уведомления сохраняются в БД. Подготовлен обработчик FCM с очередью доставки, повторами, регистрацией устройств и напоминаниями о задержанных перевозках. Проверка внешней доставки требует настоящего Firebase-проекта и телефона.

## Порядок локальной проверки

```bash
npm ci
npm run prisma:generate
npm run lint
npm test
npm run build
```

Для разработки: `docker compose up -d postgres redis s3`; база должна быть отдельной от production. Задать DATABASE_URL, REDIS_URL и S3-переменные из `.env.example`. Выполнить `npm run prisma:deploy`, `npm run seed` только в development, `npm run s3:init -w @bioflow/backend`; затем запустить API и веб. Prisma CLI читает переменную DATABASE_URL непосредственно; не полагаться на загрузку `.env` серверным модулем.

Интеграционная приёмка использует исключительно БД с суффиксом `_spec`:

```bash
DATABASE_URL='postgresql://bioflow:bioflow@localhost:5432/bioflow_spec?schema=public' \
ACCEPTANCE_API_URL='http://localhost:4110/api/v1' \
npm run test:acceptance -w @bioflow/backend
```

API для проверки должен работать с той же БД, Redis и приватным S3. Тест создаёт отдельную организацию и настоящие тестовые записи/файлы, не удаляя существующие данные. `NODE_ENV=production` запрещает демонстрационный seed.

## Развёртывание на сервере

1. Подготовить отдельные staging/production БД PostgreSQL 16 и приватное S3. Создать домен, DNS, HTTPS-сертификат и резервные копии. Не открывать PostgreSQL, Redis и API напрямую в интернет.
2. Заполнить `.env.production` по `.env.production.example` через защищённую настройку окружения. JWT/QR-секреты должны быть независимыми случайными строками длиной не менее 32 символов. S3_PUBLIC_ENDPOINT должен быть доступен браузеру/телефону по HTTPS; внутренний S3_ENDPOINT может отличаться. Настроить CORS бакета для WEB_ORIGIN командой `s3:init`.
3. Разместить сертификаты в `shared/certificates/fullchain.pem` и `privkey.pem`, конфигурацию в `shared/.env.production`, внешние ключи в `shared/secrets/`. Эти файлы исключены из Git и Docker-контекста.
4. Проверить резервную копию, затем просмотреть новые миграции. Они добавляют партийную модель и архивирование, расширяют статусы и делают водителя необязательным. Данные старых таблиц сохраняются; прежние маршруты изменения запасов блокируются. Перед запуском на существующей БД сверить прежние остатки и документы: автоматически придумывать происхождение исторических запасов нельзя.
5. Выполнить `infrastructure/deploy-release.sh RELEASE_DIR SHARED_DIR BACKUP_DIR`. Скрипт делает проверенную резервную копию до миграций, собирает production-контейнеры, проверяет API и конфигурацию HTTPS. Не использовать development Compose для production. После запуска проверить публичный health, вход, права, фото и полный производственный цикл на staging.
6. Для новой пустой БД выполнить `npm run bootstrap:production -w @bioflow/backend`, задав BOOTSTRAP_ORGANIZATION_NAME, BOOTSTRAP_OWNER_EMAIL и BOOTSTRAP_OWNER_PASSWORD через защищённое окружение. Существующие пользователи не перезаписываются. Демоданные и пароль из development не попадают в production.
7. Для push смонтировать настоящий service account и задать FCM_SERVICE_ACCOUNT_FILE. В Android передать FIREBASE_API_KEY, FIREBASE_APP_ID, FIREBASE_MESSAGING_SENDER_ID и FIREBASE_PROJECT_ID через `--dart-define`; это параметры клиентского проекта. Service-account/private key в приложение не включать.
8. Собрать подписанный Android release с окончательным HTTPS API_URL и ключом заказчика. Debug APK использует эмуляторный тестовый адрес, не является production-релизом. Проверить камеру, разрешения, push, потерю связи и синхронизацию на телефоне. iOS требует отдельного подтверждения договорного объёма.

## Резервные копии и восстановление

`backup-postgres.sh` создаёт custom dump, проверяет его структуру и сохраняет SHA256. `restore-postgres.sh` восстанавливает транзакционно только в пустую БД и отказывается перезаписывать непустую. Скрипты удаляют Prisma query-параметры из libpq URL. Локальное восстановление проверено в отдельной `bioflow_restore_spec`.

На сервере настроить ежедневное выполнение backup, хранение вне сервера и согласованные сроки хранения. S3-файлы резервируются отдельно вместе с их ключами и метаданными БД. Расписание, объём, RPO/RTO и пробное восстановление production подтверждаются после доступа к инфраструктуре. Откат контейнеров не означает откат БД; добавленные миграции не следует удалять вслепую.

## Что нельзя считать подтверждённым заранее

Работа на реальном сервере, нагрузочная ёмкость его ресурсов, внешняя доставка FCM, релизная подпись, поведение камеры/офлайна на физическом устройстве и полное визуальное совпадение всех 13 экранов. Архив содержит только один PNG; XML и ссылки не заменяют изображения остальных экранов. Локальные тесты не являются пользовательской приёмкой production.

## Развёртывание через GitHub

Ветка изменений проходит CI и открывается как PR в main. После успешных проверок и объединения доступны workflows `server-inspect` (только диагностика) и `deploy-production` (релиз, backup и проверки). Для password SSH добавьте `PROD_SSH_PASSWORD` через Settings → Secrets and variables → Actions; пароль никогда не включается в код или workflow. Вместо пароля можно использовать `PROD_SSH_KEY`. По умолчанию host `109.235.118.171`, port `22`, user `root`, deploy path `/opt/bioflow`, app URL `https://bio.app.kz`; все значения можно переопределить соответствующими прежними secrets.

Первое диагностическое соединение использует SSH accept-new и выводит публичный fingerprint. Сверьте его через консоль провайдера и сохраните проверенную строку known_hosts как `PROD_SSH_KNOWN_HOSTS`. Deploy требует этот secret, существующую защищённую production-конфигурацию и сертификаты. Запуск диагностики не устанавливает Docker, не меняет сервер и не создаёт production БД. Автоматический deploy остаётся отключённым до готовности инфраструктуры.

Текущая GitHub-интеграция возвращает HTTP 403 для Actions Secrets/Variables. Поэтому добавить секреты средствами этого сеанса невозможно; это не ограничивает отправку Git-ветки и создание PR. Значение пароля вводится только в защищённой форме GitHub.

Проверены реальная инициализация бакета и OPTIONS: разрешённый Origin получает 200, посторонний — 403. Старые локальные тома не обновлялись; проверка новой версии выполнена в отдельном хранилище.
