# HTTP-команды и русские роли — проверка 12.10.2026

## Исправлено

На Web по HTTP/IP создание партии останавливалось сообщением `crypto.randomUUID is not a function`: браузер предоставляет randomUUID только в защищённом контексте. Общий генератор команды использует native randomUUID при его наличии, иначе криптографический getRandomValues с битами UUID v4. Math.random не используется. Все три клиентских вызова заменены: ledger-команды, архивирование справочника и старый маршрут создания накладной. Существующий повтор команды продолжает использовать исходный idempotency key.

Назначение ролей пользователю теперь выполняется галочками с русскими названиями и пояснениями вместо ввода технических кодов через запятую. Каталог «Роли» показывает назначение каждой стандартной роли; таблица пользователей показывает назначенные роли. Backend возвращает текущий набор для предварительного выбора; смена пользователя через оба списка обновляет галочки. Коды и разрешения стандартных ролей не изменены. Это назначение существующих ролей; редактор произвольных ролей и разрешений в эту правку не входит.

## Подтверждено

- Web: 11 Node-тестов, в том числе 4 новых сценария UUID (native method, UUID v4 bits, 1000 криптографических значений без повторов, отсутствие криптографических API).
- Backend: 53 теста. Два новых проверяют загрузку текущих ролей для управляющего пользователями и отсутствие доступа без users.manage; passwordHash в ответ не попадает.
- Production-сборки Web и backend успешны.
- Семь UI-сценариев Chromium прошли на реальных изолированных PostgreSQL/API. Тестовый hostname сопоставлен исключительно loopback; контекст действительно небезопасный: isSecureContext=false, randomUUID=undefined, getRandomValues=function. Бизнес-ответы API не подменяются.
- До исправления: ошибка воспроизводится, POST создания партии отсутствует. После: партия создаётся через форму по HTTP. Два быстрых нажатия отправляют одинаковый ключ, в списке после повторного входа ровно одна запись.
- Каталог ролей показывает русские названия и пояснения. Новый тестовый пользователь получает две роли через галочки; после повторного входа обе сохранены и отмечены. Изменение выбора в форме блокировки также обновляет текущий набор ролей; роли владельца при проверке не записываются.

Скриншоты и results.json: `/workspace/artifacts/bioflow-http-roles-2026-10-12`. UI проверялся на desktop и снят на ширине 390 px. Working data сервера не использовались для UI-фикстур. Окончательные CI, PR и деплой фиксируются в истории GitHub Actions и итоговом локальном отчёте.

## Пользователю после обновления

1. Обновить страницу Web (Ctrl+F5) и войти своим аккаунтом.
2. «Партии и операции» → «Новая партия добычи»: заполнить поля, создать черновик и проверить его номер в списке.
3. «Пользователи»: создать пользователя или выбрать существующего в блоке «Назначить роли».
4. Отметить роли по русским названиям и пояснениям → «Назначить». Этот выбор заменяет предыдущий набор; доступ к объектам задаётся отдельно.
5. Повторно выбрать пользователя и проверить галочки и колонку «Роли». Каталог всех готовых ролей находится в разделе «Роли».

Production HTTPS по-прежнему требует DNS/сертификата; исправление UUID делает доступный тестовый HTTP-путь работоспособным и не заменяет HTTPS.
