# Тестирование на облачном сервере

Workflow `server-ops`, операция `launch-test`, собирает серверные образы, проверяет их SHA256 при доставке и запускает отдельный Compose-проект `bioflow-test` на 109.235.118.171. База, Redis, файлы и конфигурация сохраняются вне каталогов релизов. Существующие неизвестные тома/занятые порты не принимаются автоматически; при повторном запуске БД резервируется до миграций. Данные не сбрасываются и демоданные не импортируются.

Тестовый веб/API: `http://109.235.118.171/`; debug APK: `http://109.235.118.171/downloads/BIOFLOW-test.apk`. APK использует API сервера, а не Android-эмулятора. Отдельный приватный S3 публикует только интерфейс подписанных запросов на 9000; PostgreSQL/Redis/API не имеют публичных портов. Это тестовый запуск по HTTP. Для production требуется публичный DNS, HTTPS, проверка на телефоне и внешние push-ключи.

Первый пользователь `owner@bio.app.kz` создаётся с независимым случайным временным паролем и обязан сменить его при первом входе. Пароль не появляется в Git, job logs или публичных скачиваниях. Артефакт `BIOFLOW-test-access` содержит автономный HTML, зашифрованный паролем SSH из защищённого GitHub Secret. Скачайте его из выполненного Actions-запуска, откройте локально и введите SSH-пароль: расшифровка происходит в браузере без сети. При повторных развёртываниях установленный владельцем пароль не изменяется.

`bioflow-test-backup.timer` запускает копию БД и файлов ежедневно в 02:00 Asia/Yekaterinburg. Снимок файлов на короткое время останавливает только S3 и гарантированно возвращает его в работу при ошибке. Копии находятся в `/opt/bioflow-test/backups`, проверяются pg_restore/SHA256 и не удаляются автоматически. Для production нужны дополнительная копия вне сервера и проверенное восстановление.

Публичный SSH-ключ закреплён после успешного первого password-auth соединения `server-inspect` (run 37602884393); последующие подключения обязаны совпадать с ним. Он не является паролем или закрытым ключом.


## По порядку: проверка и следующий запуск

1. Откройте Web по ссылке выше либо скачайте APK на телефон и установите тестовую сборку. Она использует API этого сервера. Если Android предлагает обновление установленной сборки, данные аккаунта сохраняются штатным обновлением; при несовместимой подписи не удаляйте приложение с несинхронизированными командами.
2. Войдите существующим аккаунтом. Для первого владельца используйте защищённый BIOFLOW-test-access из Actions и смените временный пароль. Создайте необходимые справочники и пользователей через Web. Данные макетов не являются утверждёнными рабочими справочниками.
3. GitHub → Actions → server-readiness → Run workflow → main → inspect. Проверьте commit, здоровье контейнеров, backup timer и место. Эта операция читает состояние сервера.
4. Для проверки восстановления выберите verify-backup. Восстанавливается отдельная временная копия; рабочая база не перезаписывается. Пустой файловый backup отдельно отмечается в результате; непустой контрольный файл создаётся и восстанавливается только в disposable S3.
5. В панели DNS зоны app.kz добавьте A-запись bio со значением 109.235.118.171. После распространения записи выполните server-readiness / enable-https на main. Скрипт использует публичный DNS, а не локальную запись hostname в /etc/hosts, и до успешной проверки DNS ничего не меняет.
6. Откройте https://bio.app.kz/ и health; проверьте скачивание/загрузку файлов. Для production Android потребуется сборка с HTTPS API и ключом подписи владельца. Текущий IP HTTP сохранён для тестового APK.
7. Следующие изменения проводите через feature branch → PR → успешный CI → main. Затем Actions → server-ops → launch-test. Скрипт резервирует базу и сохраняет данные вне релиза; существующий HTTPS override не удаляется.
8. Отдельно подтвердите физическую камеру/QR/офлайн, Firebase push, полный цикл ролей/форм, длительную нагрузку, мониторинг и внешнее хранилище backup. Эти проверки не заменяются зелёным CI или эмулятором.
